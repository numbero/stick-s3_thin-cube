# 自动建联优化 · macOS 0.4.32（53）

2026-10-20，自动模式现在会在收到所选设备的新 BLE 广播后，取消尚未确认设备信息的 Wi-Fi 探测并立即连接 BLE。失效 Wi-Fi 地址也会短时避让，避免发现缓存再次覆盖回退目标。最终版本已构建、签名并安装到 `/Applications/ThinCube.app`，自动模式及自动重连均开启，设备保持连接。

## 同等节能状态下的实机结果

同一 Mac、同一 ThinCube-6046E5、同一 v0.4.59 固件及同一 boot，USB 供电。两组所有正式样本完成时均为 CPU 160MHz、`onlineSaving=true`。设备在两组之间没有重启，仅依次安装、启动不同版本的上位机。

| 版本 | 正式样本 | 建联中位数 | 样本 P95 | 约 5 秒 Wi-Fi 超时 |
| --- | --- | --- | --- | --- |
| 原版 0.4.31（52） | 10/10 成功 | 6.78 秒 | 8.24 秒 | 6/10 次 |
| 最终版 0.4.32（53） | 10/10 成功 | 1.90 秒 | 2.77 秒 | 0/10 次 |

本次样本中，中位数缩短约 **72%**，样本 P95 缩短约 **66%**。新版十次均记录 `redirected`，在 Wi-Fi 尝试开始后约 **43–974ms** 收到 BLE 广播并切换，无需等满五秒。原版其余四次 Wi-Fi 是快速失败，说明网络状态本身也会影响等待长度，不能把每次连接都描述为固定节省五秒。

每组保留一次预热，随后正式重启上位机十次。所有正式样本开始时未连接，结束时控制连接及本地音频准备均已就绪。使用 `scripts/benchmark-connections.py`，只启动系统应用目录中的程序；每次退出确认进程结束，间隔一秒后启动。失败记录不剔除。

计时从外部观察到硬件检查 `begin` 至 `complete`，包含自动模式的失败尝试、回退及退避。硬件检查每 200ms 轮询连接状态，脚本每 20ms 观察文件；这不是首帧声音或目标应用录音延迟。P95 使用 nearest-rank，十个样本时等于最大值。两组顺序执行、未随机交错，因此百分比仅描述本轮观测，不是所有网络或长期可靠性的承诺。

## 实现与边界

- **广播触发提前回退**：仅自动模式、同一所选设备、新收到的 BLE 广播、蓝牙可用且仍在 `.channel` 阶段时允许切换。缓存的 Bonjour 解析不再让正在等待 HTTP 的流程忽略 BLE 广播。收到并校验 Wi-Fi `/api/info` 后已进入授权阶段，此后广播不触发中断。
- **取消旧尝试**：先记录 `redirected`，再通过现有 teardown 取消 HTTP/音频准备任务并更新 generation，再开启 BLE。旧 HTTP 响应或错误不能更新新尝试、弹出旧配对提示或把连接标为失败。保留本次连接来自用户点击还是自动恢复的语义。
- **失效地址避让**：自动模式下暂时排除同一设备刚失败的 Wi-Fi 地址，期限十秒；同一地址的重复 Bonjour 更新也遵守此规则。新 IP、其他设备和手动模式不受影响，连接成功或用户主动重试会清除记录。没有替代地址时仍保留原有保存地址的重试路径。
- **抑制重复广播**：同一设备三秒内不重复发起提前回退，节流与 Bonjour 可用事件独立。它限制重复切换，不替代原有失败退避。
- **保护明确操作**：手动 Wi-Fi/BLE、模式切换事务、网络配置事务、已开始的认证/配对及已连接会话均不会被广播抢占。BLE 仍执行原有设备身份、加密及应用授权检查。

只有收到新的 BLE 广播才提前结束 Wi-Fi 探测；蓝牙不可用、设备离线或没有广播时，沿用原有探测超时和恢复流程。固件本轮未改动或刷写，继续使用已部署的 v0.4.59。
