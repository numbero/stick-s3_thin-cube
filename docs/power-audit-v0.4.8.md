# v0.4.8 功耗评估与优化顺序

日期：2026-10-11。基于当前固件和本机实际使用的 M5Unified、Arduino / ESP-IDF SDK 源码核查。本文是评估方案，本轮没有修改运行代码、烧录新固件或重建上位机。

后续用户选择优先实施闲置阶段：保留 Clawd 约 30 秒视觉睡眠，5 分钟息屏待机、10 分钟电池供电自动关机。实现及现场验证另见 [v0.4.9 三级待机](idle-power-v0.4.9.md)；本文保留最初评估的依据。

先按“已连接 Mac、静置后休息，保留拿起唤醒、A/B 操作、远程开启语音和 OTA”的场景排序。保持清醒动画、游戏、旋转和传音的原有质量；每项节能收益需用电流测量确认。

## 当前已有的省电行为

- v0.4.8 明确关闭闲置 EXT_5V 升压，实机启动读回已确认。
- 未播放音效时关闭功放；采集与播放已有互斥策略。
- 静置 30 秒进入 PET_SLEEP，背光从用户亮度降至 12，停止麦克风采集和声音互动。
- Wi-Fi / BLE 互斥启动，不是同时持续运行两个无线链路。
- 电量和充电状态已按每秒一次读取，无需为省电显著降低该频率。
- 当前 Arduino ESP32-S3 Wi-Fi 默认配置为 WIFI_PS_MIN_MODEM，工程没有覆盖。再次调用相同设置不能当成新增节能收益；本轮未用诊断固件单独读回无线状态。

## 优先实施：减少重复工作

### 1. 静止画面按变化绘制和传输

`main.cpp:175` 仍统一采用普通 33 ms、旋转 20 ms 的绘制间隔，包括 PET_SLEEP。`ui.cpp:76` 的 present 在普通模式下每次发送完整画布，约 64.8 KB；30 次/秒约为 1.94 MB/秒的像素数据。此前正式固件日志中整帧绘制及传输约耗时 15 ms，但尚未分别计时，不能将这些时间全部归于 SPI。

`pet.cpp:61` 的睡眠动作在约 1.1 秒后固定。应保留入睡、唤醒和所有活动动画的原节奏；稳定睡眠时仅在电量、连接、静音、方向或页面改变后更新画面。按键、IMU、控制命令和 OTA 继续独立处理，不依赖绘制执行。

先减少稳定睡眠的重复渲染，再推广到像素未变化时跳过传输、变化时只更新涉及的区域。目标是相同时间点保持相同像素，不以降低全部动画帧率代替优化。旋转开始、结束、重新布局、页面切换及外部清屏时必须使缓存失效，执行必要的完整刷新。

内部 RAM 已较紧张，不直接新增第三块 64.8 KB 内部画布；评估复用非旋转阶段的现有旋转缓存，或使用经过验证的其他缓存策略。仅跳过 SPI 后还需控制主循环轮询频率，避免省下绘制时间后反而更频繁地空转。

### 2. 音频完全闲置后关闭编解码器

这里存在一个具体的代码路径：进入睡眠时先停止麦克风，再播放 Sleep 提示音。提示音结束后，`sound_effects.cpp:48` 调用 Speaker.end；固定 M5Unified 的 StickS3 扬声器关闭回调只降低功放 GPIO，没有执行 ES8311 的模拟电路关闭序列。

与此同时，`audio_input.cpp:39` 仅在 running 从 true 变为 false 时调用 Mic.end。播放提示音前 running 已变为 false，后续重复 audioTick(false) 不会再次执行 Mic 的 ES8311 关闭回调。因此，代码路径提示音效后编解码器可能仍留有模拟供电；尚未在“入睡音效已结束”的最终状态实测寄存器和电流，不能把它当作已量化的漏电。

建议用统一的音频电源状态管理：麦克风、扬声器任务都已停止且没有马上需要启动的音频时，执行一次编解码器待机关闭，并读回确认；下一次播放或采集由对应完整启动流程恢复。避免逐轮 I2C 写入，覆盖播放失败、取消、静音、休息和语音抢占路径。

唤醒后验证首个有效音频帧、第一声提示音、是否出现爆音及连续采集。不能因为当前未传音就关闭清醒时的麦克风：`voice_state.h:15` 明确保留本地声音互动以及已允许语音且连接就绪时的采集准备，这属于现有功能。

### 3. 缓存状态，减少重复 JSON 和队列操作

`device.cpp:489` 每 40 ms 构建一次完整 cJSON；其中包含不随帧变化的设备信息、每次重复转换的会话字符串，以及每次查询的 OTA 启动状态。可缓存稳定字段和已完成的启动验证状态，复用构建对象或固定缓冲，维持现有状态新鲜度和响应格式。

麦克风关闭时，audioTick(false) 仍在每轮重置已空的队列；BLE 待机也会每轮清空音频队列。可以将这些操作集中到状态转换或确实有待清理数据时执行。必须保持回调停止后的队列清理顺序，以及错误重试、切换、断线和重连的清理语义。

这一组预计属于较小收益，优先考虑实现简单且可明确证明行为一致的部分。

## 需要实机验证的进一步优化

### 4. 稳定休息时 CPU 降频

当前 CPU 为 240 MHz，没有应用层调频策略。候选是在稳定 PET_SLEEP、麦克风和扬声器均停止、无 OTA/配网/连接切换时先试 160 MHz，再评估 80 MHz；处理唤醒、游戏、旋转、采集、播放、升级等活动前恢复 240 MHz。频率切换仅发生在状态转换，不反复逐轮切换。

当前 Arduino 核心提供 setCpuFrequencyMhz，但它不同于 ESP-IDF 的自动电源管理。网络后台任务、双核行为、计时、I2C/SPI 和 USB 调试都必须参与验证；不能把 CPU 频率降低比例当成整机功耗降低比例。

本机 framework 为 Arduino 2.0.17 / ESP-IDF 4.4.7，实际使用 qio_opi 预编译 SDK。sdkconfig 未启用 CONFIG_PM_ENABLE 和 CONFIG_FREERTOS_USE_TICKLESS_IDLE。直接增加 esp_pm_configure 调用或仅补编译宏不能为预编译库补齐自动调频与自动轻睡眠支持。

### 5. 按任务截止时间等待，减少空轮询

当前主循环在两次绘制之间通常 delay(1)，每轮仍执行 UI、IMU、设备控制和其他状态逻辑。可逐步分离输入、传感器、控制、渲染与电量任务的截止时间；有按键、姿态、控制命令或采集完成时提前唤醒。

没有待处理任务时阻塞至下一个必要事件，活动时维持足够频率。不能仅拉长统一 delay：这可能增加按键、翻转或手动开启语音的响应时间；且当前没有自动轻睡眠支持，阻塞本身不会带来完整硬件轻睡眠收益。

### 6. IMU 休息模式

固定 BMI270 驱动禁用 advanced power save，并启用加速度、陀螺仪和温度。BMI270 支持低功耗加速度及运动中断，可研究只在稳定休息阶段使用，运动触发后恢复完整采样。

这属于次级优化：当前姿态与方向策略用陀螺仪约束运动速度，直接关闭陀螺仪或降低采样会改变判定。需处理旧样本、传感器恢复时间和首批数据有效性，验证轻拿、翻转、快速摇晃及两个游戏。芯片数据手册的微安模式数字不能作为整机待机电流预测。

## 无线和真正硬件休眠的边界

上位机 Wi-Fi 心跳目前为 100 ms，BLE 为 200 ms；`DeviceModel.swift:664` 在状态超过 400 ms 未更新时释放快捷键和音频会话，设备控制租约为 1 秒。将待机心跳简单延长到 1 秒，会与现有保护规则冲突。

可在后续同时改造双方协议：稳定休息时使用较小的状态报文，事件立即上报；根据双方明确确认的待机状态调整心跳，活动前恢复快速更新。兼容旧客户端时仍保留原行为，不放宽传音或持键时的失联保护。优先减少单次报文和无用请求，再评估间隔变化。

WIFI_PS_MAX_MODEM 的接收延迟受 listen interval 影响，广播接收也可能受影响；降低发射功率可能增加弱信号重传。两者都需在不同信号质量下测量，不能列为无条件省电开关。BLE 可以研究按活动状态调整连接参数，但当前 SDK 的控制器 sleep mode 有效配置为 0，后续还需核查并启用实际的控制器休眠支持。

后续重建支持 CONFIG_PM_ENABLE、Tickless Idle 的框架后，可评估 Wi-Fi Modem-sleep 配合自动 Light-sleep，让无线维持连接。需要处理音频及显示驱动的电源锁、PSRAM/USB、A/B 与 IMU 唤醒源，并控制高频任务唤醒；这是一项独立工程，不适合通过孤立 API 调用插入当前主循环。

M5PM1 关断 ESP32 供电或 deep sleep 能进一步降低功耗，但需要重新启动和恢复连接，会改变电脑远程控制及即时语音体验，适合作为用户选择的长期离线休息模式。L3B 同时涉及背光和音频，关闭它也会改变屏幕可见性；保留当前可见睡眠画面时应先做其他优化。

## 验证与建议顺序

第一批：稳定睡眠按变化刷新、音效结束后的编解码器待机关闭、低成本的状态/队列缓存。第二批：稳定休息降频与按事件调度。第三批：双方无线协议节能及支持自动轻睡眠的框架。

每项分别测量，固定设备、电池电压、亮度、无线方式和路由器信号；至少比较清醒待命、休息且保持 Mac 连接、休息但没有 Mac 连接、持续传音四种状态。记录平均电流、峰值与任务耗时，并验证 A/B、拿起、翻转、首个音频帧、原音频质量、掉线保护、重连、游戏和 OTA。

M5PM1 接口提供电压和充电状态，当前代码没有可用于测量整机平均电流的遥测。USB 输入读数含供电路径和充电影响，不能直接代表电池待机电流；测量电池侧电流或进行同条件放电对比，再报告续航增幅。本轮只有源码与官方资料核查，没有新增电流、续航或性能测试。
