# 对讲机模式：B 键与动作快捷键调研

调研日期：2026-10-18。依据当前工作区固件 v0.4.38、Mac v0.4.15 源码，以及 M5Stack、Bosch 官方资料。本文是设计建议，未修改产品代码、构建应用或操作设备；识别率、误触率、续航和响应时间均未进行本轮实测。

## 建议结论

建议按以下顺序演进：**先把 B 短按开放为可配置的一次性快捷键，再增加左右小幅倾斜；摇晃和机身双敲放在实验功能中验证。** A 继续承担按住/松开的实时控制。动作类输入默认关闭，由用户逐项开启、绑定；不替用户预设 Enter、Esc 等可能影响当前应用的组合。

B 在对讲机模式下可选择「快捷键 / 麦克风静音 / 不执行」。已有用户升级保留静音；用户明确选择快捷键后，B 短按只执行所绑定的组合，不同时静音。非对讲机状态暂时保留 B 原行为，Mac 原有麦克风静音入口继续可用。B 长按切换连接、配对及恢复出厂入口仍由系统优先处理。

上述优先级是结合现有代码作出的工程判断，并非官方承诺的手势识别效果。当前“静音是否低频”只有本次用户反馈，没有使用统计；据此适合提供选择，不宜直接删除麦克风静音能力。

## 1. 现有能力和边界

| 项目 | 当前实现 | 对扩展方案的影响 |
| --- | --- | --- |
| A 快捷键 | 传音、倒置、已就绪且重新按下 A 才保持组合键；松手释放 | 这是 hold 输入，不能直接等同于一次性手势 |
| B 短按 | 本地切换麦克风静音，并持久保存；配对/OTA 等页面另有取消操作 | 需要设备端调整动作路由，单改 Mac 映射无效 |
| B 长按 | 按住约 3 秒，松开时切换 Wi-Fi/BLE | 若 B 按下就发快捷键，长按切换前已经产生副作用 |
| A+B | 空闲时同时按住 3 秒、两键松开重新配对；B/combo 会抑制 A | 不能直接增加 A+B 普通快捷键，也不能假定 A/B 可同时独立注入 |
| 开机按住 B | 进入恢复出厂确认页，再短按 A 确认、B 取消 | 配置只作用于正常运行，不覆盖启动及确认页面 |
| 摇晃 | 已有 `MEV_SHAKE`，驱动 Clawd 晕眩动画 | 有原型基础，但识别策略尚不足以直接触发系统操作 |
| 姿态 | 已有正立、倒立、朝上/朝下、横置、运动中，以及横屏游戏倾斜算法 | 可复用三轴采集和部分数学工具，不照搬整套姿态语义 |
| 可靠传输 | A 的 `edge:{seq,down}`、32 项队列、重传及心跳 ack | 现协议没有输入来源；新动作混入旧 edge 会被旧 Mac 当作 A |

## 2. 可选输入比较

下表可靠性是待验证的相对判断，成本只比较本项目改动范围。

| 输入方式 | 建议输出 | 主要问题 | 建议定位 |
| --- | --- | --- | --- |
| B 短按 | 一次按下并自动松开 | 要与 3 秒长按、系统页面仲裁 | 第一阶段；收益最确定 |
| 左倾 / 右倾后回正 | 左右各一次快捷键 | 普通持握变化、方向定义、语音姿态边界 | 第二阶段优先 |
| 有意识地左右摇一组 | 一次快捷键 | 普通移动、拾起、放下；还会把机械噪声带进麦克风 | 实验开关 |
| 手指轻敲机壳两下 | 一次快捷键 | 按 A/B、桌面振动、放下设备易混淆；采样链路待补齐 | 第三阶段实验 |
| 单敲机壳 | 一次快捷键 | 很难与一次普通碰撞区分 | 不建议作为常规输入 |
| 短促向左/右拧一下 | 两个相对方向的快捷键 | 陀螺仪积分、回程重复触发、轴定义 | 可选后续探索 |
| 前倾 / 后仰后回正 | 两个快捷键 | 与改变说话角度、朝上/朝下姿态更易重叠 | 左右倾斜验证后再评估 |
| 倒置 / 正立 / 朝上 / 朝下 / 横置 | 会话与电源动作 | 已承担进入语音、退出、休息和游戏 | 第一版保留原语义 |
| A 双击 / 长按 | 单次或保持 | A 必须立即按下；等双击会拖慢，立即发则无法撤销 | 不优先扩展 |
| B 双击 | 额外一次快捷键或静音 | 若单/双击必须互斥，单击必须等待双击窗口 | 高级选项，不默认启用 |
| A+B / 电源键 | 系统动作 | 配对、下载、复位/关机等入口冲突 | 保留系统用途 |
| 声音/拍手 | 一次快捷键 | 对讲机正在采集语音，环境声音难作明确控制意图 | 不建议纳入这一轮 |

StickS3 配有 BMI270 六轴 IMU、A/B 可编程按钮、麦克风和红外；官方板载清单没有电容触摸面或磁力计。六轴足以估计相对重力的倾斜、短时角速度和冲击，但不能据此承诺绝对罗盘方向，也不能直接知道手指敲的是机身哪一面。[M5Stack 产品文档](https://docs.m5stack.com/zh_CN/core/StickS3)

## 3. B 键：推荐短按脉冲，保留长按系统操作

### 推荐交互

1. 对讲机开启并处于有效倒置语音状态时，B 短按在**松手确认后**发送一个 `b_click`；Mac 执行一次所绑定的组合，并在短时间后自动释放。
2. 用户可在按键页把 B 改回「麦克风静音」或「不执行」。快捷键是 Mac 本地组合；设备只需要知道 B 的角色，不保存 macOS 键码。
3. B 按住达到 3 秒后，松手只切换连接方式，取消这次 click。系统页面的 B 取消、开机 B 恢复出厂保持优先。
4. 按下时锁定这次操作的上下文。若在按下到松开期间退出语音、断线或进入系统页面，取消这次快捷键；不要在松手时重新解释为静音。新会话中必须松开再按。
5. 第一版新增脉冲不与 A 持有同时执行：A 尚未松开时的 B 或手势直接消费、不排队；A 松开后再按 B。需调整现有仲裁，避免 B 的 `suppressA` 在对讲机中意外把 A 提前释放。非语音状态的 A+B 配对逻辑保留。

例子仅用于说明：A 绑定语音软件的按住说话键，B 绑定用户选定的确认组合。用户先松开 A，再短按 B。ThinCube 只能提交键盘事件，不能证明目标应用已经完成识别或接受了确认。

### 为什么第一版不把 B 做成另一枚实时保持键

| B 策略 | 收益 | 代价 | 判断 |
| --- | --- | --- | --- |
| 松手确认短按，自动按/松 | 保留 3 秒切换，行为可互斥 | 不适合第二个按住说话键 | 推荐 |
| 按下立即注入，松手释放 | 支持另一组实时 hold | 必须取消/迁移语音模式下 B 长按切换，否则长按意图已触发快捷键；还需重做 A/B 并发 | 后续按需选择 |
| B 单击快捷键，双击静音 | 设备上仍有静音入口 | 单击要等待双击判定；若不等待，双击会先触发一次快捷键 | 不作为默认 |

当前固定 M5Unified 的 hold 默认阈值为 500 ms；`wasClicked()` 在短按松开时成立，`wasSingleClicked()` / `wasDoubleClicked()` 则等点击计数决定后成立。应用另行实现 3 秒切换，因此约 0.5–3 秒的 B 持有目前通常不触发短按静音。建议第一版保留这一短按边界及中间时长无动作的行为，并在 UI 明示；需要改变时再单独设计，不把所有少于 3 秒的松手都突然当成快捷键。[官方 Button API](https://docs.m5stack.com/zh_CN/arduino/m5unified/button_class)、固定版本源码 [Button_Class.hpp](https://github.com/m5stack/M5Unified/blob/8b63555e7bd9ac71978c55ad868fd1d1d3b2ef3e/src/utility/Button_Class.hpp) / [Button_Class.inl](https://github.com/m5stack/M5Unified/blob/8b63555e7bd9ac71978c55ad868fd1d1d3b2ef3e/src/utility/Button_Class.inl)。

单击/双击互斥要等窗口这一点是事件时序上的必然限制。若未来需要 B 双击，宜独立设置约 250–350 ms 的应用判定窗口，而非直接改变库的 hold 阈值；具体值需手感验证。

## 4. 姿态与动作识别方案

以下数值均为**原型起始范围，尚非验收规格**。先验证动作可分辨，再决定默认灵敏度，不宣称支持率或固定端到端时延。

### 左右小幅倾斜：最值得增加的动作输入

- 面向用户定义「屏幕左侧降低 / 右侧降低」，不随 LCD 180° 旋转反转含义。进入对讲机、停稳且两键松开后建立一次握持基准；中立区内可缓慢校正，动作过程中冻结基准。
- 起始建议：偏离基准约 15–25° 并保持 150–250 ms 才确认；回到基准 ±6–8°、稳定约 150 ms 后才能再次触发。持续倾斜不重复发键，回正动作也不触发另一方向。
- 使用低通后的重力方向，合加速度明显偏离 1g 时暂停倾斜识别，防止把甩动当倾斜。左右各映射一个 pulse，不持续按住方向键。
- 当前姿态进入倒置要求竖轴占比约大于 .82，且有其他轴限制；小角度选择是为保留语音姿态余量。先验证不同握姿下的实际余量，不能直接把阈值定到接近横置。确认退出语音姿态时清空候选，保留原退出规则。
- 可复用 `LandscapeTilt` 的相对角度、死区思路；现有游戏函数的轴与横屏方向不能直接搬入倒置握持。

依据：[固定轴姿态阈值](../firmware/src/pose_detector.h)、[相对倾斜工具](../firmware/src/landscape_input.h)。

### 摇晃：重写快捷键识别策略，不直接转发动画事件

现有代码是在 800 ms 内，选择绝对值较大的 x/y 轴后累计 4 次符号变化，并与拾起共用时间门限。它没有完整的去重力、同一主轴幅度、动作前后停稳判定；主导轴切换也可能改变符号。这个策略适合动画原型，尚无足够依据用于系统快捷键。[当前摇晃实现](../firmware/src/motion.cpp)

建议保留动画策略，另写独立的输入识别器：短窗口内冻结主轴，使用去重力后的有符号动态加速度，检查正负峰的幅度、交替次数和间隔；动作结束、稳定后只发一次。可从约 0.8–1.2 秒内出现 2–3 次完整往返、结束稳定 150–250 ms、冷却 1–1.5 秒开始试验。幅度门限由实测分布确定。

仅接受在同一有效语音会话中开始和完成的摇晃；中途确认正立/平放/横置则取消，不为了摇晃破坏原语音退出规则。连续摇晃不循环触发。传音中的机身动作会产生机械拾音噪声，这是交互代价，不能仅靠 IMU 过滤解决。

### 双敲机壳：可行，但驱动接入成本明显更高

Bosch 的 BMI270 **不同配置镜像支持的算法不同**。Legacy 配置提供 single/double/triple tap、orientation/flat 等；当前固定 M5Unified 加载的 8192 字节镜像与 Bosch base 镜像逐字节相同，没有 tap 上层接口。不能因为芯片叫 BMI270，就认定当前固件已提供可用的双敲事件。固定驱动的实际接口、配置镜像、量程、采样率和中断路径核对见[一手资料证据笔记](walkie-input-imu-primary-research-2026-10-18.md)。[Bosch 官方功能分组](https://github.com/boschsensortec/BMI270_SensorAPI/blob/master/README.md)

两条技术路线：

- **软件识别**：保留当前配置，增加足够频率的加速度采集及有界环形缓冲，以峰形、峰间隔、冲击后的振铃消除区识别两次独立轻敲。先以约 200 Hz 的数据获取目标做可行性原型，测量真实有效样本与漏样；不能只把主循环调用频率提高就声称采样达标。当前空闲轮询最多约 25 Hz，不能直接复用为短冲击检测链路。[当前采集](../firmware/src/motion.cpp)、[省电轮询周期](../firmware/src/power_save_policy.h)
- **Legacy 硬件识别**：接入 Bosch 官方 Legacy 配置和 API，按官方采样条件启用 tap，再消费对应状态/中断。它需要额外验证 IMU 初始化、量程换算、寄存器所有权和既有 any-motion 深睡唤醒，不是加一个 if 即可。[Bosch SensorAPI](https://github.com/boschsensortec/BMI270_SensorAPI)、[既有唤醒事务](../firmware/src/motion_wake_registers.h)

当前驱动读取 data-ready 及最新寄存器，没有启用/消费 FIFO。按驱动初始化与 Bosch 复位值推断，加速度通常为 100 Hz、±8g，陀螺仪为 200 Hz、±2000°/s；这些是源码推断，实际运行值仍需回读。提高到软件敲击原型所需采样率时，要检查加速度的新样本位：`M5.Imu.update()` 非零也可能只是陀螺仪更新，不能把旧加速度重复计作新峰。量程修改还必须同步 M5Unified 的换算，防止破坏所有姿态阈值。Legacy 官方 tap 的 user-data 路径要求 200 Hz，内部数据路径也有专门条件，详见[Legacy AN002](https://www.bosch-sensortec.com/media/boschsensortec/downloads/application_notes_1/bst-bmi270-an002-01.pdf)及证据笔记。

先验证「拿在手中，用手指轻敲机身两下」。桌面双敲受材质、距离与同桌动作影响，应作为另一种单独实验。设备无法仅凭一次冲击可靠区分敲击、放下与邻近振动。按键按下/松开附近应屏蔽 tap 候选，但屏蔽时长要实测，避免快速从 A 操作切换至双敲时漏触发；同一次动作最多归属一个手势。

## 5. 统一事件和 Mac 映射

第一阶段就应建立带来源的输入模型，否则以后每加一个手势都要修改一条专用链路。

建议分三层：设备生成 `a` 的 down/up，或 `b_click/tilt_left/tilt_right/shake/double_tap` 的 pulse；控制协议负责可靠送达；Mac 按来源查本地绑定并执行。一次性动作由 Mac 自动配对按/松，初始可沿用现有测试使用的约 100–150 ms 脉冲范围，再按目标软件验证；不依赖网络再次传回 release。

### 兼容与可靠性要求

1. **能力协商**：完整状态新增可选 `inputCaps` / 版本；Mac 在当前 epoch 显式订阅新版输入并确认就绪。旧固件只显示 A；旧 Mac 只收到原来的 A edge。绝不把新动作伪装成旧 A edge，否则会触发错误映射。
2. **独立新版队列与确认**：建议新版事件包含 `seq/source/phase/session`，心跳增加独立 `inputAck`；同一新协议中的 A 与脉冲共享有序队列。新旧 A 路径择一执行，避免双发；旧字段保留只为兼容，不把两条队列的 ack 混用。当前每次确认移除一项队首，Mac 心跳为 Wi-Fi 约 100 ms、BLE 约 200 ms，连续事件会有排队开销。单次动作应只占一个 pulse 事件；批量发送/累计确认可后续设计，第一版不改变现有 ack 的语义。
3. **防延迟重放**：绑定 epoch 和语音 session，并携带设备端可计算的事件年龄；过期、停止/断线/切换、校准或会话变化时清空。不能直接相减 Mac 和 MCU 的绝对时钟。失效事件仍确认并记录丢弃原因，恢复后需新动作。
4. **注入仲裁**：第一版只允许一组系统组合保持，新增 pulse 在 A 物理保持时就消费掉，不延后执行。Mac 还需处理 A release 在传输队列里尚未到达的情况，按有序事件执行；任何异常转入释放，而非让用户的确认键稍后突然发出。现有 `KeyInjector` 本身拒绝上一组尚保持时再次 press，不能简单给每个来源各建一个注入器来规避。[现有注入器](../macos/Sources/ThinCube/KeyInjector.swift)
5. **上下文与故障清理**：只在语音已就绪、有效倒置、映射已订阅时生成快捷键；配网、配对、OTA、游戏、校准、睡眠和连接切换优先。退出/锁屏/断线/编辑绑定时，释放全部来源、取消自动释放任务和候选，重新按下或回正后才武装。保留原 Mac 状态超时释放策略。[原协议](thincube-protocol-v1.md)
6. **设置一致性**：Mac 保存各来源组合；固件保存 B 角色和已启用手势/灵敏度。先完成能力检查和设备角色确认，再在 UI 显示启用成功。升级保留原 A 与 B 静音；旧客户端不触发新来源，且不能因不认识 B 角色而静默把同一次操作改回静音。
7. **语音范围**：本轮继续以对讲机语音条件为门槛。若未来希望静音、未准备音频或普通桌面模式也能遥控，另设遥控模式与控制就绪状态，避免为了快捷键被迫开启麦克风。

## 6. 上位机呈现

现有「按键」页可扩为「按键与手势」，保持已有快捷键录制、直接选择及左右修饰键设置。基础区域显示 A 与 B；手势区域逐项启用并显示绑定，实验项明确标注。B 的角色选择与快捷键编辑放在同一行附近，避免用户以为改了组合就已经改变设备端行为。

每行同时显示触发语义，如 A「按住保持，松开释放」、B「短按松手后执行一次」、倾斜「回正后可再次触发」。提供检测测试：先只显示最近识别的动作和拦截原因，由用户主动开始注入测试。诊断记录来源、seq、会话、识别/拦截和已提交事件；“已提交”不写成目标应用成功。

进入对讲机后可短暂显示 B 的当前用途；退出后恢复原提示。传音反馈使用屏幕，避免为确认手势抢占麦克风播放提示音。[当前快捷键编辑器](../macos/Sources/ThinCube/ShortcutEditor.swift)、[既有音频优先策略](../firmware/src/sound_policy.h)

## 7. 实施阶段与验收

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| 1 | 新输入协议/协商；B 角色及短按绑定；单次注入；迁移 | Wi-Fi/BLE 下 B 短按可用，B 3 秒与系统页面无泄漏；旧端兼容；断线及 A/B 交错无卡键 |
| 2 | 新手势策略层；左右小倾斜；摇晃实验；检测界面 | 基准/回正/一次触发成立；普通持握和退出姿态不误发；音频队列和控制链路不受明显影响 |
| 3 | 双敲采样原型，比较软件与 Legacy；决定是否产品化 | 轻敲/按键/放下/桌振可分辨；实际采样与资源开销合格；睡眠唤醒回归通过 |

建议的原型验收门槛（产品目标，不是当前结果）：

- 每项动作在 Wi-Fi/BLE、USB/电池、手持/可适用的桌放条件分别重复至少 30 次；先以有意动作命中率 ≥95% 为继续试验门槛，并记录漏触发类型。样本量小，不能由此推断长期可靠性。
- 正常说话、按 A/B、拾起、放下、插拔线、缓慢换握姿、桌面敲击及横屏玩法作为负样本；至少 30 分钟日常操作无快捷键误发后，才考虑从实验项转为常规功能。持续摇晃必须最多产生一次。
- 单独测量「识别完成到系统事件」和「完整动作到系统事件」的中位数/高分位，Wi-Fi/BLE 分开；短按松手、双击等待、手势确认与心跳排队是不同来源的延迟，不拿阈值之和冒充实测。
- 覆盖重复/迟到事件、丢 ack、队列满、重连换 epoch、音频 session 切换、A 持有中操作 B、编辑/锁屏/退出、进入/取消长按、恰在按住期间进入对讲机；任何路径不得遗留合成按键。
- 手势启用前后比较音频丢帧、主循环耗时、IMU 有效采样率和电池电流。高频采样只在启用并进入相应交互时运行；深睡唤醒动作只唤醒，不在启动后补发快捷键。

这些是后续实施的工作与验收范围。本轮完成源码和一手资料调研，尚未得出任何实机识别效果或功耗结论。
