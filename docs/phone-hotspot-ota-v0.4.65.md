## 使用

手机先把 `thincube-v0.4.65.bin` 下载到本机文件。进入设备热点有两个入口：

- **设备按键**：按住正面 A，随即短按电源/复位键开机或重启；继续按住约两秒，看到 `Release A` 后松开。初始 A+B 组合不进入手机升级或恢复出厂；B-only 保留原恢复出厂确认。
- **Mac 固件页**：通过当前已配对的蓝牙或 Wi-Fi 连接点击“用手机升级…”。设备接受后约 700 ms 重启开启热点。旧固件不显示可用能力，需先通过原 Mac OTA 或 USB 更新。

按屏幕显示连接 `ThinCube-Update-xxxxxx`，输入本次随机热点密码，在完整 Safari/Chrome 打开 `http://192.168.4.1/`。输入设备六位升级码，选择应用 `.bin`；网页显示设备、当前/目标版本、大小及 SHA-256。新的一次设备 A 点击才确认具体镜像；B 或网页取消按钮可取消接收。不要上传整片备份、bootloader 或分区表。

网页发送到 100% 后还要等设备完成写入与镜像校验。只有最终 HTTP 200 且 `{ok:true}` 才报告成功；断线后没有最终回包会提示查看设备，不根据发送字节数或 `done` 快照推断成功。进入最终校验后取消可能被拒绝，此时保持供电。

等待时 B 退出；失败时 B 先返回维护等待页，再按 B 退出，也可以直接在网页重试。五分钟无有效操作自动退出，系统门户探测不续期；确认、接收、校验和提交阶段不会被闲置退出打断。成功或退出通过重启恢复原 BLE/Wi-Fi 模式，保留原配对、网络和校准。Mac 发起后暂停重连，退出热点后点击“退出热点后重新连接”；回包丢失单独提示“设备响应未确认”。

## 实现

`maintenance.cpp` 独占 AP-only、DNS 和 HTTP 服务，提供内置离线页面、设备信息、临时授权及现有 OTA 路由，不注册普通配对、设置或控制接口。12 位随机热点密码、六位升级码及 32 位十六进制 token 每次会话重新生成，只在 RAM 保存；五次错码后退避 30 秒。手机不索取或替换 Mac 长期密钥。

Mac 请求保存在单个 `tcmaint:request` 记录中，下一次启动先消费并提交清除，再决定是否开热点，避免断电导致维护启动循环。该记录与永久 `tcmode` 连接选择分开；恢复出厂、旧网络/连接事务和待验证新镜像先执行各自恢复规则。物理入口整次按住与松开被消费，十秒卡键会取消进入；每轮具体 OTA 再以 generation 和松键门禁要求新的 A 点击。

HTTP worker 独占 OTA 句柄：按 A、长度与首块型号/芯片/声明版本检查通过后才擦备用槽。流式摘要和 `esp_ota_end` 验证成功后才切换启动分区。接收→最终校验与取消在同一锁内仲裁，超时检查和 CONFIRM/READY→FAILED 同样原子执行；时间差使用有符号比较，避免 HTTP 时间戳比本轮主循环新几毫秒时误判超时或立即重启。页面所有脚本和 SHA-256 均内置，HTTP 私网 IP 下不依赖 `crypto.subtle` 或 CDN。

## OTA 回滚修复

Arduino 2.0.17 默认会在 `initArduino()` 中过早确认新固件。现在以强 C 符号 `verifyRollbackLater()` 返回 true，将 `PENDING_VERIFY` 保留到本项目的 60 秒自检；90 秒仍不健康则请求回滚。最终 ELF 已确认该符号为强符号，反汇编返回 1。

自检验证本地屏幕、IMU、音频资源和相应无线/门户资源。路由器离线不单独判失败；STA 已关联时必须完成本地 HTTP 注册，服务启动失败不能借无线模式已启用而通过。首次连接选择页面有独立资源条件。维护请求在 pending 阶段被拒绝，继续正常启动检查；不提前确认来进入热点。

未预存网络的设备升级后可能进入首次连接选择或热点配网。用户在 60 秒内选连接方式、成功配网时会保存操作，自动重启延后至启动健康确认通过，屏幕显示 `CHECKING` / `Checking firmware`；避免一次正常设置操作触发试启动回滚。

## 验证范围

- 正式与 Base 固件构建通过；正式应用镜像 **1,844,592 字节**，SHA-256 `1ff0726e958b3c149982132310090ff6c1b93f6c3107c3b58f41fdff8a68f956`，在现有 2 MiB 槽内。
- 本地 CPU/Python/SDK 检查、离线页面 Node 检查和 Swift **142 项测试全部通过，无跳过**，包括新构建镜像识别。
- 真实 `ota.cpp` 在 host port 上执行 **44 个 ASan/UBSan 场景**：鉴权/确认、擦除前拒绝错镜像、备用槽写入、断连/损坏/写入失败、取消边界、超时竞态与健康确认。仅替换 include 块，不复制状态机；摘要桩用于控制失败，真正 SHA-256 由页面标准向量、边界和整包交叉校验覆盖。
- 手机宽度浏览器预览初始页和授权选文件页，无横向溢出，控制台错误为空。浏览器预览使用 localhost 模拟设备，不代表 iPhone/Android 连真实热点已验收。
- Mac 已签名并安装到 `/Applications/ThinCube.app`，保留旧版安装备份；原生界面确认存在“手机热点升级”和“用手机升级…”入口。
- USB 设备 `7c:e8:b1:e2:db:38` 已完整备份 8 MiB。原 app0 为 v0.4.64，bootloader 与本机构建产物逐字节一致，安全启动及 Flash 加密均关闭。新版写入 app1，只增加第二 OTA 选择扇区；首次启动前设备 MD5 确认 NVS、bootloader、分区表、原 app0 和应用槽之外区域全部未变。
- 真机试启动已确认新槽保持 `PENDING_VERIFY`；受控重启后自动运行原 app0 / v0.4.64，验证异常试启动恢复。最终镜像另行写入 app1 并独立运行，约 89 秒后读取到第二 OTA 记录 `seq=2, state=VALID` 且 CRC 有效；设备 app1 MD5 与最终镜像一致。再次重启的日志确认 `v0.4.65`、`running app1`、`ota state : valid`，后续心跳正常。原 app0、bootloader/分区表及应用槽之外区域校验仍与备份一致；设备设置未执行清除。

证据和可分发 `.bin`/清单位于本机 `artifacts/phone-ota-v0.4.65/`（忽略目录），包括源码状态机测试日志、安装备份校验、整片 Flash 备份、试启动/回滚日志及手机页面预览。手机实机上传、设备 A/B 的手感和两个入口的完整现场流程仍需实际操作验收。原生 Mac 验收时系统提示旧蓝牙绑定失效，当前连接未成功，因此只确认了新入口的展示，不将其当作真实 BLE 发起成功。USB/JTAG 监控重连可能额外复位试启动设备，健康窗口验证应避免监控本身干扰。
