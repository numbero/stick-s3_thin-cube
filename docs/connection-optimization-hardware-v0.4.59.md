# 首批建联优化实机验证 · 固件 v0.4.59

2026-10-20，同一台 Mac 与 ThinCube-6046E5，USB 供电。新固件已刷入设备，上位机最终恢复为 `/Applications/ThinCube.app` 的 0.4.31（52），自动连接设置恢复为测试前的 `automatic`。最后一次状态检查确认控制连接在线、本地音频已准备、未传音，设备运行超过五分钟，配对及校准仍有效。

## 固定 BLE 对照

| 组合 | 正式样本成功数 | 建联中位数 | 样本 P95 |
| --- | --- | --- | --- |
| A：上位机 0.4.30（51）＋原固件 v0.4.58 | 10/10 | 2.34 秒 | 3.03 秒 |
| B：上位机 0.4.31（52）＋原固件 v0.4.58 | 10/10 | 1.92 秒 | 2.34 秒 |
| C：上位机 0.4.31（52）＋新固件 v0.4.59 | 10/10 | 1.27 秒 | 1.71 秒 |

A→B 的中位数缩短约 18%，B→C 再缩短约 34%；A→C 总计缩短约 **46%（1.07 秒）**，样本 P95 缩短约 43%。这是本轮组合对照的观测结果，无法据此分摊每一个代码改动的独立贡献。

方法：固定 BLE 模式，保留既有配对，每组先运行一次预热并保留记录，再连续重启系统应用目录中的上位机十次。每次退出确认进程结束，间隔一秒后启动；所有正式样本开始时均未连接，完成时均为 `connected=true`、`audioPrepared=true`。失败会原样保留，不进行择优剔除，本次三组没有失败。

统一计时从外部首次观察到硬件检查 `begin` 到 `complete`。两版上位机都以 200ms 轮询连接状态，外部脚本每 20ms 观察一次文件；该口径含观察误差，表格仅保留两位小数。`complete` 检查上位机控制连接完成，音频准备状态另行记录；它不等于固件音频租约确认或首帧声音。P95 使用 nearest-rank，十个样本时就是最大值，不能作为长期总体 P95 或可靠性承诺。

各组顺序执行，没有随机交错；结果适用于这台设备已经配对、USB 供电、重启上位机的固定 BLE 场景，不覆盖设备冷启动、深睡唤醒或纯 Wi-Fi 的提速幅度。

## 埋点与功能检查

- C 组十次连接均报告初始间隔 12×1.25ms＝15ms，直接满足快连接条件；设备侧 `performance_ready` 在链路建立后 **4–23ms** 出现，相关计时行 `lost=0`。
- C 组上位机里程碑中位数：本地音频桥 80ms、BLE channel 720ms、认证 991ms、有效状态 1090ms、控制连接 1091ms。音频桥在握手期间完成；各阶段中位数来自不同样本，不能相减解释为某阶段独占耗时。
- 进行两秒传音检查，接收 226 帧、渲染 104065 个样本，`concealed=0`、`bleAudioDropped=0`。仅保存计数与状态，没有保存 PCM。该检查证明短时传输与本地渲染工作正常，不代表目标应用录音质量或长时间稳定性验收。
- BLE→Wi-Fi 在 7.24 秒完成，Wi-Fi→BLE 在 3.39 秒完成，两次设备事务均为 `committed`；结束时连接正常、未传音。
- 串口观察中未发现 panic/assert，最后健康行显示音频健康、IMU 读取错误为零。切换引起的重启属于正常事务流程；最终只读状态快照显示同一 boot 已运行约 315 秒，电源采样失败计数为零。

## 自动模式与剩余瓶颈

恢复原来的自动模式后又执行三次重启，3/3 成功，完整耗时分别为 **8.27、6.80、6.81 秒**。每次日志均显示先发起 Wi-Fi 尝试，在约 5011–5012ms 失败，随后 BLE 回退成功；因此固定 BLE 的 46% 改善不能直接用于自动模式的整体等待时间。当前最值得继续处理的是端点选择和失效 Wi-Fi 地址的等待。

较长空闲后的检查还观察到间隔被降到 72 单位（90ms）；一次传音恢复中的 `performance_ready` 到 3.13 秒才出现。初始快间隔复用已生效，但原来的空闲降速/恢复策略仍会影响长空闲场景，本轮没有修改该策略。最终处于空闲节能状态时的 90ms 间隔属于正常现有行为。

最早进行过一组未固定传输的原版探索测试，数据另存于 `A-old-mac-old-firmware/`。它受端点选择与重试影响，不与 A/B/C 合并，也不据此声称自动模式提速。
